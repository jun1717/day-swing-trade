reference_high の決め方の比較検証（RH-A / B / C / D / E）

検証期間 2026-02-12 〜 2026-07-22 ／ 対象 near.max_position_in_range = 0.65 で発生した ENTRY_CANDIDATE 32 件（仮想ENTRY成立 32 件）× 5 案 ／ WARNING 開始条件は VARIANT A、warning_low 割れ後は CLOSE_BREAK に固定 ／ 生成日 2026-08-11

このレポートの読み方（先に必ず読むこと）

  • 今回変えたのは reference_high の決め方だけ。 ENTRY ロジック、near.max_position_in_range = 0.65、 初期STOP range_lower × 0.995、WARNING 開始条件、 warning_low の定義、押し安値候補の計算方法、 trail = 押し安値 × 0.995、STOP を下方向へ動かさないこと は 5 案とも完全に同一で、今回いっさい触っていない。 固定利確も導入しておらず、新しい%閾値も探索していない。
  • WARNING 開始条件は VARIANT A、warning_low 割れ後は CLOSE_BREAK（仮想EXITは翌営業日始値）に固定した。 どちらも「今回の変数を reference_high だけに絞るための研究上の基準」であって、 正式採用ではない。前 2 回の検証の結論は保留のままである。
  • RH-A〜RH-E はいずれも比較用の仮説であって正式ルールではない。 「trail 成立件数がいちばん多い案」や「仮想利益がいちばん高い案」を 自動的に採用する、という使い方はしない。
  • 同じ日に「終値で warning_low 割れ」と 「high > reference_high」の両方が成立する日がある。 日足では先後を決められないので AMBIGUOUS_REHIGH_EXIT_ORDER として分離し、 REHIGH 優先 / EXIT 優先の両方を走らせて差分を出している。 どちらが正しい順序かは決めていない。
  • これは収益バックテストではない。母数が小さく、 「どの案が正しいか」を成績で決められる規模ではない。

12. §18 look-ahead bias

確認項目実装上の担保テスト
RH-A は WARNING 発生時点までのデータだけを使用`holding_high` は日次ループの中で当日の足まで反映した running max。警戒足を開く `_open_warning` の呼び出し時点の値をそのまま固定し、以後書き換えない。test_RH_Aは警戒足当日までの高値だけを使う
RH-B は WARNING 当日の OHLC だけを使用`reference_high = bar.high`。その足以外は参照しない。test_RH_Bは警戒足自身の高値になる
RH-C は WARNING 前日までの close だけを使用終値ベースの running max は日次処理の**最後**に更新する。同じ日に開いた警戒足の `reference_high` には当日の終値が入らない。test_RH_Cは警戒足当日の終値を含まない
RH-D は WARNING 当日の open だけを使用`reference_high = bar.open`。その足以外は参照しない。test_RH_Dは警戒足の始値になる
RH-E は WARNING 前日までの high だけを使用当日の足を running max に入れる**前**の値を渡している。警戒足自身の上ヒゲは入らない。test_RH_Eは警戒足当日の高値を含まない
REHIGH はその日までのデータで判定`high > reference_high` をその営業日の足だけで評価する。翌日以降の足はループの中で一度も参照しない。test_REHIGHはその営業日の足だけで判定する
new_swing_low_candidate は REHIGH 確定時に初めて確定押し安値は「警戒足の日から**今日まで**」の安値の最小値。`min_low_value` は毎日更新され、再突破した日の値でそのまま確定する。test_押し安値は再突破日までの安値だけで決まる
trail stop は REHIGH 翌営業日からのみ有効確定した STOP は `pending_stop` に入り、翌営業日の寄りで `active_stop` に入る。確定した当日の安値には遡って適用されない。test_trail_stopは翌営業日から有効
EXIT 後の未来値を判定には使用しないEXIT 後にどこまで伸びたかは追跡が終わったあとに集計する。状態機械は EXIT 時点で閉じており、その後の足で挙動が変わることはない。test_EXIT後の値動きは状態遷移に影響しない_RH
prefix invariant を各 RH 案で満たす系列を先頭から k 本で打ち切って再実行しても、その時点までに確定していた REHIGH・押し安値・STOP 引き上げは変わらない。test_prefix不変性_5案いずれでも成立する
prefix 不変性テストを 5 案に拡張した。 系列を先頭から k 本で 打ち切って再実行し、フル実行の結果と一致するかを RH-A〜RH-E すべてで確認している。 その時点までに成立していた REHIGH の日付、押し安値、STOP 引き上げの内容と 有効化日は打ち切っても変わらない。

変異チェックも行った。 次の 3 通りに書き換えると look-ahead テストが失敗し、 元に戻すと全 243 件が通ることを確認している。
  • RH-C の終値 running max を日次処理の先頭で更新する（＝警戒足当日の終値が reference_high に混ざる）→ 1 件失敗
  • RH-E に当日の足を入れた後の holding_high を渡す （＝RH-A と同じになる）→ 4 件失敗
  • REHIGH 判定を bars[d+1].high で行う → 7 件失敗 （今回のテストだけでなく、既存の exit_state_machine / warning_break のテストも落ちる）
既存出力の回帰も確認済み。 rh_rule の既定値は HOLDING_HIGH（＝従来の定義）なので、 research/exit_state_machine/ の CSV 7 本、 research/warning_start_study/ の CSV 7 本、 research/warning_break_study/ の集計 CSV は いずれも数値がバイト単位で以前と同一である。 唯一の差分は warning_break_study/events.csv の timeline_summary 列に AMBIGUOUS_REHIGH_EXIT_ORDER の 表示が増えたことで、これは今回 §7 に従って それまで黙って REHIGH 優先で処理していた同日成立を明示したためである。 判定も数値も変わっていない。

13. §21 の 14 の問いへの回答

1. RH-A/B/C/D で REHIGH_CONFIRMED 件数はどう変化したか
警戒足に対する REHIGH の成立率は 7/26 (27%) / 10/27 (37%) / 11/27 (41%) / 14/29 (48%) / 8/26 (31%)（RH-A/B/C/D/E の順）。RH-A が最も少ない。ハードルを下げれば成立は増えるが、WARNING → REHIGH までの営業日数の中央値は 1.0 日 / 1.0 日 / 1.0 日 / 1.0 日 / 1.0 日 でどの案も変わらない。つまり緩めても「早く」なるのではなく、それまで成立しなかった件が成立するようになるという変化である。警戒足の件数自体も案によって動く（26 件 / 27 件 / 27 件 / 29 件 / 26 件）。REHIGH すると WARNING を抜けて次の警戒足が出るので、分母も一緒に変わる点に注意。
2. trail stop 成立件数はどう変化したか
1 回以上引き上げたイベントは 6/32 (19%) / 9/32 (28%) / 8/32 (25%) / 11/32 (34%) / 6/32 (19%)、2 回以上は 0/32 (0%) / 0/32 (0%) / 2/32 (6%) / 2/32 (6%) / 1/32 (3%)、更新の総回数は 6 回 / 9 回 / 10 回 / 13 回 / 7 回。初回引き上げまでの営業日数は 5.0 日 / 6.0 日 / 4.0 日 / 4.0 日 / 5.0 日、初期STOPからの引き上げ幅は +7.28% / +5.88% / +5.55% / +5.22% / +7.28%。緩い案ほど件数は増えるが、1 回あたりの引き上げ幅は小さくなる。低い位置で押し安値が確定するので当然の結果で、STOP を ENTRY 価格より上へ持ち上げられた件数は 5/32 (16%) / 5/32 (16%) / 6/32 (19%) / 6/32 (19%) / 5/32 (16%) とほとんど動かない。
3. 現行 RH-A が厳しすぎるという仮説は支持されたか
方向としては支持されたが、程度は小さい。RH-A は 5 案の中で必ず最も高い水準で、REHIGH 成立率も最小（7/26 (27%)）。§4 で問題視した「警戒陰線自身が最高値を作り、その天井をもう一度抜くことが再上昇の条件になる」構造は実在し、10/26 (38%) で起きていた。ただしその構造を取り除いた RH-E（警戒足前日までの高値）でも REHIGH は 8/26 (31%) にしかならず、RH-A の 7/26 (27%) からほとんど動かない。「厳しすぎるから拾えない」より「その水準に戻ってくる相場がそもそも少ない」方が効いている。
4. RH-B <code>warning_high</code> は「警戒足を否定して再上昇」という意味で自然に機能するか
意味としては自然だが、期待したほど別物にならない。10/26 (38%) は RH-A と同一値で、その場合「警戒足を否定する」ことと「保有中最高値を抜く」ことが同じになるため、いちばん問題が出やすい場面でだけ RH-A と区別がつかない。差がある残りでも RH-A との差は中央値 -0.46%（16/26 (62%)） と小さい。結果として trail 成立は 9/32 (28%)、trail EXIT 後にさらに +10% 以上伸びたのは 2/7 (29%)。
5. RH-C の終値ベースは、現在の日足・終値中心の運用と自然に整合するか
整合する。本システムは元レンジ上限の突破を終値で判定し、warning_low 割れも（今回の固定条件では）終値で判定している。「調整終了」だけを高値（上ヒゲ）で測る現行 RH-A は、その中で唯一ヒゲ基準が混ざっている場所である。RH-C はそこを終値ベースに揃える案で、RH-A より低い幅は中央値 -1.36%（23/26 (88%)）、REHIGH 成立は 11/27 (41%)。ただし判定そのものは 5 案とも high > reference_high のままで、終値で判定しているわけではない。「終値で作った高値を、ザラ場で超えたか」を見ている点は残る。
6. RH-D は緩すぎる兆候があるか
ある。RH-D は 5 案の中で14/26 (54%) と最頻の最安水準で、REHIGH 成立は最多（14/29 (48%)）、trail 成立も最多（11/32 (34%)）。しかしその trail で降りた後にさらに上昇したケースが、+3% 以上 10/11 (91%)、+10% 以上 6/11 (55%)、EXIT 後に保有中最高値を更新したのが 8/11 (73%)。「陰線の始値を一度上回った」だけでは調整終了の判断として弱いことを示している。
7. +5% / +10% 以上伸びたケースの利益吐き出しは改善したか
ほとんど改善しない。これが今回いちばん重要な結果である。最大含み益 +5% 以上（23 件）で最大利益のうち残せた割合の中央値は -3.53% / -3.53% / -3.53% / -3.53% / -3.53%、+10% 以上（16 件）でも 1.40% / 1.40% / 0.98% / 0.98% / 0.98%。吐き出し幅の中央値も 12.65% / 12.14% / 12.47% / 12.47% / 12.65% とほぼ横並びで、reference_high をどう変えてもこの穴は埋まらない。trail を上げられた件数は増えるのに残せた利益が増えないのは、低い位置で押し安値が確定した trail は、上昇の途中で当たってしまうからである（Q8）。
8. trail 成立を増やす代わりに、正常な調整で早く降りる副作用は増えたか
明確に増えた。trail STOP で降りたイベントのうち、EXIT 後にさらに +3% 以上上昇したのは 5/5 (100%) / 6/7 (86%) / 8/8 (100%) / 10/11 (91%) / 6/6 (100%)、+10% 以上は 2/5 (40%) / 2/7 (29%) / 5/8 (62%) / 6/11 (55%) / 3/6 (50%)、EXIT 後に保有中最高値を更新したのは 4/5 (80%) / 5/7 (71%) / 7/8 (88%) / 8/11 (73%) / 5/6 (83%)。EXIT 後の上昇率の中央値は +4.82% / +4.82% / +16.40% / +13.14% / +12.24%。trail 成立件数と早降りは同じ現象の裏表で、片方だけを増やすことはできていない。「trail が立った」ことと「利益を確保できた」ことは別である。
9. STUCK_IN_WARNING / INITIAL_STOP_EXIT_AFTER_BREAKOUT は減ったか
STUCK_IN_WARNING は 5/32 (16%) / 6/32 (19%) / 6/32 (19%) / 5/32 (16%) / 5/32 (16%)、INITIAL_STOP_EXIT_AFTER_BREAKOUT は 4/32 (12%) / 4/32 (12%) / 4/32 (12%) / 3/32 (9%) / 4/32 (12%)。どちらも reference_high では動かない。STUCK は warning_low を日中に割ってから終値で確定するまでの猶予で発生するもので、前回の検証で CLOSE_BREAK を採った時点でほぼ解消済み。上限突破後に初期STOPまで戻る件も、そもそも reference_high に届かないから trail が立たないのであって、水準を下げても大半は救えていない。
10. fractal 方式と比べて、押し安値をより自然なタイミングで確定できたか
「早い／遅い」ではなく「見ている安値が違う」。RH-A では今回の方法で 7 件の押し安値を確定したが、fractal も同じ安値を認めたのは 1 件だけで、6 件は今回のみ、6 件は fractal のみが認識した。案を緩めると今回側の確定は増える（7 / 10 / 11 / 14 / 8 件）が、一致件数はほとんど増えない（1 / 2 / 2 / 2 / 1 件）。確定日を比べられた件では今回が先／同日／fractal が先が 0・0・1 / 2・0・0 / 1・0・1 / 2・0・0 / 0・0・1。今回の方式は fractal より早いというより、fractal が拾わない安値を押し安値として採っている。「自然な時系列判定になっているか」という問いには、右側の足を待たずにその日で確定できる点は自然だが、採っている安値がチャート上の押し目と一致しているとは言い切れないと答えるほかない。
11. 4 案の中に、チャート構造・運用方法の両面から明らかに不自然な案はあるか
RH-D（warning_open）は不自然である。陰線の始値は「その日にたまたま寄った値」で、チャート構造として何かの節目ではない。同じ形の陰線でも寄りが高ければハードルが上がり、低ければ下がる、という再現性のない基準になる。実測でも最も緩く（14/26 (54%)）、早降りの副作用が最大だった（Q6・Q8）。

RH-E は不自然ではないが、RH-A とほとんど区別がつかない。RH-A より低くなるのは +0.00%（10/26 (38%)） だけで、これは「警戒足自身が最高値を作った」場合に限られる。切り分け用としては意味があったが、独立した案としての存在意義は薄い。残る RH-A / RH-B / RH-C はどれも節目として説明でき、この 3 つに明らかに不自然なものはない。
12. 4 案の中に、正式ルール候補として次の統合検証へ持っていく価値がある案はあるか
ある。ただし「成績がよいから」ではない。持っていく価値があるのは RH-C（前日までの終値高値）で、理由は 2 つ。(1) 現行の運用がレンジ上限突破も warning_low 割れも終値で判定しているのに、調整終了だけがヒゲ基準になっている不整合を解消する（Q5）。(2) RH-A より確実に低く（-1.36%（23/26 (88%)））、かつ RH-D のように「その日の寄り値」という恣意的な水準ではない。RH-A も候補から外せない。今回の数字は RH-A を否定していない（Q7 のとおり利益保持はどの案でも変わらず、早降りの副作用は RH-A が最小）。RH-D は外してよい（Q11）。RH-B / RH-E は RH-A との差が小さすぎて、単独で検証する価値が薄い。ただしこれは候補の絞り込みであって、採用の決定ではない。
13. まだ reference_high の定義を追加で検証する必要があるか
reference_high の水準をこれ以上いじる必要はない。5 案は ENTRY 比で中央値 2.02% のハードル差しかなく、その範囲では利益吐き出しが改善しないことが Q7 で確認できた。ただし、水準ではない部分に未検証の論点が 2 つ残っている。(1) 再突破の判定を high ではなく close にすること。今回は §7 の指定どおり 5 案とも high > reference_high で固定したので、この軸は一度も動かしていない。日足・引け後判断との整合という Q5 の論点は、水準より判定側に効く可能性がある。(2) 押し安値の取り方そのもの。Q8 のとおり trail が立っても利益が残らないのは、押し安値が WARNING 期間の最安値（＝直近の投げ）に張り付くためで、これは reference_high ではなく押し安値側の問題である。いずれも今回の指示の範囲外なので、実装も検証もしていない。
14. それとも次の「EXIT統合検証」へ進める段階か
reference_high 単独の比較としては、これで材料は出そろっている。5 案の性質・自然さ・副作用は Q1〜Q11 のとおり整理できた。ただし、統合検証に入る前に決めておくべきことが 2 つある。(1) 同日に REHIGH と利確候補が両立した日の扱い（§7）。順序不明の日は案ごとに 3 / 3 / 5 / 5 / 4 日あり、その日を含むイベントは全件、順序次第で結果が変わった。全体の中央値はほとんど動かないが、これはルールとして先に決めておかないと統合検証の結果が再現しない。(2) Q13 の (1)（判定を close にするか）。reference_high の水準と判定方法を同時に動かすと、また原因が分からなくなる。

この検証では正式ルールの変更を行っていない。どの案を採用するかも決めていない。
